# egfg 設計仕様（フェーズ G）：コード生成と、推定プログラムの対戦場（arena）の土台

- 日付：2026-10-06
- 状態：承認済み（2026-10-06、ユーザーの指示「その順で進めて」による。内容は随時見直す）
- 前提：フェーズ F（`2026-10-06-low-rank-design.md`）

## 1. 目的

egfg が作る推定プログラムと、LLM が個別に書いた推定プログラムを、同じ条件で比べられるようにする。そのための土台として、次の 4 つを作る。

1. コード生成：egfg が抽出した計算を、実行できる Python（numpy）の関数に書き出す。
2. 問題の書式：因子グラフの構造と、表の作り方（種類と性質）だけを書いた JSON。表の値そのものは含まない。
3. 採点の仕組み：プログラムの正しさと速さを、新しい乱数の表で測る。
4. 取り置きの問題：改善する側に見せない検証用の問題を、手続き的に生成する。

この土台の上で、二者（良いプログラムを書く LLM と、egfg を改善する LLM）の対戦を数ラウンド試し、採点に抜け穴がないかを確かめる。その後、問題を作る敵役を加えた三者の対戦と、定期的な自動実行に進む（別の段階）。

## 2. 推定プログラムの約束

どちらの側のプログラムも、次の形の Python モジュールにする。

```python
def infer(tables: dict[int, numpy.ndarray]) -> dict[str, numpy.ndarray]:
    """因子の番号 -> 表（軸は因子のスコープの順）を受け取り、
    変数名 -> 正規化した周辺分布（和が 1）を返す。"""
```

- 求めるのは全変数の周辺分布（この段階では）。
- プログラムは問題の JSON（構造と表の性質）を見て書いてよいが、表の値は実行時にしか渡されない。
- numpy 以外のライブラリは使わない（scipy なども使わない）。
- 前処理（表の分解など）も `infer` の中で行い、その時間も計測に含める。

## 3. 問題の書式

```json
{
  "name": "chain8_k8",
  "variables": {"x0": 8, "x1": 8},
  "factors": [{"id": 0, "scope": ["x0", "x1"], "table": {"kind": "dense"}}],
  "tags": ["in_scope"]
}
```

- 表の種類：`dense`（一様乱数 [0.1, 1)）、`lowrank`（非負の乱数行列の積。`rank` と `split` で、どの変数の分け方で何ランクかを示す）。
- タグ：`in_scope`（egfg の今の範囲）と、範囲を広げる目標の印（この段階では使わない）。
- 採点のとき、問題ごとに乱数の種から表を作る。種は採点のたびに変える。

## 4. コード生成

- 抽出した `Dag` を、トポロジカル順に並べた直線的な numpy のコードにする。
- 積は `numpy.einsum`（結果の軸は変数名の順）、和は `sum(axis=...)`。
- 和の連続とその下の積（ほかから使われていないもの）は、1 つの `einsum` にまとめる（積と和の融合）。
- 最後に各根の表を正規化する。
- 低ランク分解を使う計算では、分解（特異値分解）も生成するコードの中で行う。
- 生成したコードは、`evaluate` の結果と一致することをテストで確かめる。

## 5. 採点

各問題・各プログラムについて：

- 正しさ：新しい乱数の表を 3 組作り、参照の周辺分布（変数が 12 個以下なら総当たり、それより多ければジャンクションツリー）との最大誤差が 1e-6 以下か。
- 速さ：`infer` の実時間を、温めの 1 回のあと 7 回測った中央値。
- egfg の側だけ：コンパイル時間（探索と抽出とコード生成）と、演算回数（コストモデル）も記録する。
- プログラムは子プロセスで実行し、時間（1 回 60 秒）とメモリ（4 GB）の上限を付ける。
- 結果：問題ごとに「egfg の時間 ÷ LLM の時間」。全体は幾何平均。誤りのある側は、その問題で負けとする。

## 6. 問題の集合

- 公開の問題（`arena/problems/`）：鎖、星形、ランダムな木、輪、格子、ランダムな疎グラフ、HMM の展開など。状態数と大きさを変えたもの（20 問程度）。低ランクの表の問題も含める。
- 取り置きの問題：同じ種類の生成器で、改善する側に見せない乱数の種から作る（`arena/holdout.py` が実行時に生成する）。egfg の改善を採用するかは、取り置きの問題での成績で決める。

## 7. 二者の対戦（この段階での試行）

1 ラウンドは次のとおり。

1. 「書く側」の LLM が、公開の問題ごとに推定プログラムを書く（`arena/solutions/llm/<問題名>.py`）。
2. 採点する。
3. 「改善する側」の LLM が、結果と LLM のプログラムを見て、egfg（規則、表現、探索、コード生成）を改善する。改善は別のブランチにし、次の条件をすべて満たすときだけ採用する。
   - 既存のテストがすべて通る。
   - 足した規則は、乱数での評価と総当たりとの一致で確かめる。
   - 取り置きの問題での成績が悪くならない。
4. 結果を `arena/rounds/<番号>.md` に記録する。

この段階では、ラウンドを手元で数回だけ回し、採点の抜け穴（答えの埋め込み、範囲外への逃げ、ベンチマークへの過剰な合わせ込み）がないかを確かめる。

## 8. 範囲外（次の段階）

- 問題を作る敵役（三者の対戦）。
- 定期的な自動実行（スケジュール、別のセッション）。
- C などへのコード生成。
- フィルタリング・正規分布の問題（まずは離散の全周辺分布だけ）。
