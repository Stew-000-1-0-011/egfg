# egfg 設計仕様（フェーズ J）：出力コードを短くする ― 同じ形の計算の関数化とループ化

- 日付：2026-10-07
- 状態：草案（承認待ち）
- 前提：フェーズ G の C のコード生成（`src/egfg/ccodegen.py`）

## 1. 目的

今の C のコード生成は、DAG のノード（積、和、融合した和と積）ごとにループの入れ子を 1 つずつ展開する。そのため、コードは DAG のノード数に比例して長くなる（鎖 128 変数で 2,673 行・81KB）。gcc の時間が支配的になり（同じ例で 27 秒）、LLM が書いたコードの約 4 倍の長さになる。

egfg は DAG の段階で計算の構造を知っているので、そこで次の 2 つを行い、短いコードを出す。

1. 同じ形の計算を 1 つの関数（カーネル）にまとめ、呼び出しにする。
2. 同じカーネルの呼び出しが、被演算子の位置が規則的にずれながら続く部分を、ループにする。

あわせて、抽出のコストにコードの大きさ（カーネルの種類の数）を入れる選択肢を作る。

問い：

- H21（短さ）：大きめの問題で、行数と gcc の時間が大きく減る（目安：鎖 128 変数で 1/5 以下）。
- H22（速さ）：実行時間は、今のコードと比べて大きくは悪くならない（目安：±20% 以内）。
- H23（抽出）：カーネルの種類の数をコストに入れると、演算回数をほとんど増やさずに種類が減る。

## 2. 形（カーネルの同値類）

ノード 1 つのループの入れ子は、次で決まる。

- 出力の変数の並び（ソートした名前順）と、それぞれの状態数。
- 和をとる変数と、その状態数。
- 被演算子ごとの、各変数の歩幅（その配列での位置の重み）。

変数を出力・和の中での位置で名前を付け替えると、名前によらない「形」が得られる。形が同じノードは、配列のポインタだけが違う同じ計算である。

- 形ごとに `static void kN(double *out, const double *a, const double *b)` を 1 つ出す。状態数と歩幅は定数として埋め込む（gcc の展開とベクトル化が効くように）。
- 各ノードは、そのカーネルの呼び出し 1 行になる。

## 3. 呼び出しのループ化

- 中間の結果の配列を、出力の形（大きさ）ごとに 2 次元のプール（`static double poolN[個数][大きさ]`）にまとめる。
- トポロジカル順に並んだ呼び出しのうち、同じカーネルが連続する区間を探す。その区間の中で、各被演算子が次のどれかなら、ループ 1 つにまとめる。
  - プールの、区間の中での位置について 1 次式（a·i + b）の番号の要素。
  - 入力の表の、1 次式の番号の要素（`tables[a·i + b]`）。
  - 区間の中で変わらない配列。
- 条件を満たさない呼び出しは、そのまま 1 行で出す。
- 区間の中の順序はそのまま保つので、前の呼び出しの結果を次で使う場合（鎖の前向きの計算など）も正しい。

## 4. 抽出のコスト（任意）

- ノードの形は、そのノードと子のスコープだけで決まる（e-node ごとに事前に計算できる）。
- 貪欲な抽出の DAG のコストに、「使われる形の種類の数 × α」を足すオプションを作る（既定は α = 0）。

## 5. 範囲

- 離散の C のコード生成（arena で使うもの）。低ランク分解の部分（分解の計算）はそのまま。
- 線形ガウスのコード生成（`gccodegen.py`）は範囲外（同じ考え方は使えるので、結果を見て次に決める）。
- 正しさの約束（`infer` の引数と出力）は変えない。今のコード生成も残し、オプションで選べるようにする。

## 6. 実験

- 問題：arena の公開 16 問、大きめの 5 問、分割を使った鎖 64・128 変数、格子 6×6。
- 測るもの：行数、バイト数、gcc の時間、実行時間（arena と同じ測り方）、カーネルの種類の数、ループにまとめた呼び出しの割合、α を変えたときの演算回数とカーネルの種類の数。
- 成果物：`results/short_code.csv`、`experiments/SHORT_CODE_REPORT.md`。

## 7. テスト

- 新しいコード生成の出力が、今のコード生成と同じ周辺分布になる（いくつかの種類のグラフ、分割あり、低ランクあり）。
- 鎖で、呼び出しがループにまとまる（コードの行数が、鎖の長さによらずほぼ一定になる）。
