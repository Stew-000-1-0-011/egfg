# egfg 設計仕様（フェーズ M）：生成した C に合わせたコストのモデルと、実測による較正

- 日付：2026-10-07
- 状態：承認済み（2026-10-07）
- 前提：フェーズ G・J の C のコード生成（`src/egfg/ccodegen.py`）、フェーズ K の実測（`results/partition_search.csv`）

## 1. 目的

今のコスト（`cost.py`）は、演算回数だけを数える。積は結果の表の大きさ、和は元の表の大きさである。しかし、フェーズ K の実測では、これが C の実行時間とずれていた。

- 演算回数が 3% 以上少ない計算が遅かった組が、300 組中 75 組（25%）あった。
- 鎖 64 変数では、演算回数が 29% 少ない計算のほうが遅かった（8 組すべてで逆転）。
- 演算回数が同じ計算どうしで、実行時間が最大 1.55 倍違った。

ずれの原因は、コード生成がしていることをコストが知らないことである。

- **融合**：和の連続と、その下の 1 か所でしか使わない積は、1 つのループの入れ子になる。中間の表は作られず、演算回数で数えた「積」と「和」は、1 回の掛けて足す演算になる。
- **メモリ**：中間の表を書き、後で読む量。読む順番が飛び飛びかどうか（いちばん内側のループの歩幅）。
- **ループの手間**：入れ子の数と深さ。小さい入れ子が多いと、計算そのものより手間が大きい。

そこで、生成される C の構造からコストを計算するモデルを作り、係数を実測で合わせる。そのコストを抽出と分割の探索に使う。

問い：

- H30（予測の精度）：較正したモデルは、学習に使っていない問題で、C の実行時間を中央値の相対誤差 25% 以内で予測する。また、2 つの計算のどちらが速いかを、演算回数より正しく当てる。
  - 対象は、予測の差が 10% 以上ある組。
  - 目安は、正答率 90% 以上（演算回数は 75%）。
- H31（使って速くなるか）：このモデルで抽出と分割の探索をした C は、演算回数で選んだ C より速い。目安は、幾何平均で 10% 以上。
- H32（何が効くか）：較正した係数から、実行時間を決めている要因（演算、メモリ、ループの手間、融合）の割合を報告する。

## 2. モデル

### 2.1 入れ子への分解

コード生成と同じ規則（`_fusion` と `_refs`）で、DAG を「入れ子」の列に分ける。

- **融合した和**：出力の変数を外側、和をとる変数を内側に持つ 1 つの入れ子。最内で被演算子 k 個の積を足し込む。
- **積**：出力の変数の入れ子で、2 つの被演算子を掛けて書く。
- **出力**：周辺分布の正規化。

### 2.2 入れ子ごとの特徴

入れ子ごとに次を数える（どれもコード生成と同じ配列の並びで決まる）。

| 記号 | 意味 |
|---|---|
| N | 最内の本体を実行する回数（全ての変数の状態数の積） |
| k | 最内で読む被演算子の数 |
| W | 書く要素の数（出力の表の大きさ） |
| S | 最内の変数について、歩幅が 1 でない（飛び飛びに読む）被演算子の数 × N |
| L | 入れ子 1 つ（関数の中のループの組 1 つ） |
| D | ループの数（入れ子の深さの和。ループに入る手間） |
| B | 中間の表のバイト数の合計（キャッシュに収まるかの目安） |

### 2.3 予測

予測時間 = a·Σ N·k + b·Σ W + c·Σ S + d·(入れ子の数) + e·Σ(外側のループの回数) + f·[B がキャッシュを超えた分]

- 係数 a〜f は 0 以上として、実測に最小二乗で合わせる（非負の最小二乗法）。
- 係数は計算機ごとに違うので、較正の結果をファイル（`results/cost_calibration.json`）に置き、`EGFG_COST_CALIBRATION` で別のファイルを指定できるようにする。
- 較正のファイルがないときは、演算回数のコストを使う（今の動作）。

## 3. 較正のデータ

- 問題：
  - arena の公開 16 問、大きめの 5 問。
  - フェーズ K の 11 問。
  - 状態数を変えた鎖、輪、格子（K = 2〜32）。
- 計算（1 問あたり 5〜15 個）：
  - JT
  - 分割なし（解ける大きさのみ）
  - 固定の予算 4〜8
  - 分割の探索
  - 木抽出と貪欲な抽出
  - e-graph からランダムに選んだ計算（ばらつきを作るため）
- 測り方：arena と同じ（`time_c`、7 回の中央値）。問題は 1 つずつ順番に測る。
- 学習と評価：問題の単位で、5 つに分けた交差検証。同じ問題の計算は、学習と評価に分けない。

## 4. 抽出と探索への組み込み

- `optimize(..., cost="flops"|"c")`（既定は今と同じ `"flops"`。結果を見て既定を決める）。
- **貪欲な抽出**：今の貪欲な抽出は、DAG 全体のコストを関数で計算している。そこで、その関数を「選んだ DAG を入れ子に分けて予測時間を足す」ものに置き換える。融合は DAG の参照の数で決まるので、DAG 全体で数える必要がある。
- **木抽出・ILP**：ノードごとのコストしか扱えないので、融合しない場合の予測時間をノードのコストとして使う（近似）。この近似の影響も実験で測る。
- **分割の探索**：局所問題のコストを予測時間にする。クラスタの境目では、メッセージは必ず表として書かれる（融合しない）ものとして数える。
- 低ランク分解の部分（分解の計算）は、演算回数を時間に直す係数 1 つで扱う（今回は細かく作らない）。
- compact 版の C（フェーズ J）は範囲外とする。plain 版で較正する。arena では、今と同じく両方を試して速いほうを選ぶ。

## 5. 範囲外

- コード生成に合わせた書き換え（融合しやすい形への書き換えなどを e-graph の規則に入れる）は、モデルができてから次に決める。
- 線形ガウス（`gccodegen.py`）のコストの較正。

## 6. 実験

- **予測の精度（H30）**：交差検証での相対誤差。演算回数との比較として、組の順序の正答率と、問題ごとの順位相関を出す。
- **使って速くなるか（H31）**：フェーズ K の 11 問と arena の 21 問。
  - `cost="flops"` と `cost="c"` で、分割の探索（または分割なし）と貪欲な抽出を行う。
  - 出てきた C の実行時間を比べる。
  - 較正に使った問題と使っていない問題を分けて報告する。
- **何が効くか（H32）**：係数と、各項が予測時間に占める割合。
- 成果物：`results/cost_calibration.json`、`results/cost_model.csv`、`experiments/COST_MODEL_REPORT.md`。

## 7. テスト

- 入れ子への分解が、コード生成と一致する（入れ子の数と各入れ子の回数が、生成した C のループと同じ）。
- 較正のファイルがないとき、`cost="c"` は演算回数のコストと同じ結果になる。
- `cost="c"` の抽出の結果が、正しい周辺分布を与える（小さなグラフ 1 つ）。
