# egfg フェーズ K 実装計画：分割の切り方と境目のメッセージの探索

**Spec:** `docs/superpowers/specs/2026-10-07-partition-search-design.md`

## 仕様で決めきれていなかった点の扱い

1. **メッセージの名前**：今はクラスタの番号（`msg:c>j`）で付けている。分割が変わると番号が変わり、同じ局所問題を見分けられない。木の上で、2 つのつながったクラスタの間の辺は 1 本なので、その辺のクリーク（`msg:i>k`、i が送る側）で名前を付ける。こうすると、局所問題の中身（クリーク、入力、問い）だけで結果を覚えられる。
2. **全体のコスト**：つなぎ合わせた DAG はクラスタをまたいで共有しないので、全体の演算回数 = 各局所問題の抽出の演算回数の和になる。状態ごとに局所問題を全部作り直し（安い）、覚えていないものだけを解く。
3. **手の採用**：優先順位の順に試し、全体が厳密に減る最初の手を採用する（first improvement）。採用したら最初から見直す。1 周して採用がなければ止める。
4. **JT より悪くしない**：各局所問題は種（JT の計算）を入れて解き、抽出が種より悪ければ種の DAG を使う。始めの状態（1 クリーク = 1 クラスタ）は JT と同じ計算になる。
5. **ノード上限**：飽和がノード上限に達した局所問題を含む手は採用しない（始めの状態は除く）。
6. **候補の木**：全ての木で合併だけを行い、最良の木を選ぶ。交換と境目の探索は、選んだ木でだけ行う（時間を抑えるため）。
7. **メッセージの分割（3.1）**：e-graph の中を探す代わりに、送る側の項目（因子と、入ってくるメッセージの片）を、和をとる変数でつながる成分に分ける。成分ごとの片は「その成分の積の和」で、e-graph が和を積の内側へ押し込んで得る形と同じである。片が 2 つ以上になる辺だけが候補になる。
8. **周辺分布の持ち主（3.2）**：変数ごとに、持ち主のクリーク（その変数を含むもの）を記録する。既定は、今と同じく番号が最小のクラスタの中のクリークとする。

## File Structure

- `src/egfg/decompose.py`
  - メッセージの名前をクリークの辺で付ける。
  - `local_problems` に、持ち主（`owner`）と分けて送るメッセージ（`split`）の引数を足す。
- `src/egfg/partition.py`（新規）
  - 状態（クラスタ、因子の置き場所、持ち主、分けて送る辺）
  - 手の列挙
  - 覚えた解
  - 探索の本体：`search_partition`
- `src/egfg/pipeline.py`：`optimize(..., partition="budget"|"search", partition_time_s, max_cluster_vars, boundary)`。
- `tests/test_partition.py`：3 件。
  - 正しさと JT 以下（格子・輪・木。境目の探索ありとなし）
  - 単調に減る
  - メッセージの分割が選ばれる例
- `experiments/partition_search.py`、`experiments/PARTITION_SEARCH_REPORT.md`、`results/partition_search.csv`。
