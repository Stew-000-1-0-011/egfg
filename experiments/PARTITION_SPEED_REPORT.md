# 実験レポート（フェーズ L）：分割の探索を速くする

- 日付：2026-10-07
- データ：`results/partition_speed.csv`、ログ：`results/partition_speed.log`
- 再現：`uv run python experiments/partition_speed.py --out results/partition_speed.csv`（問題は 1 つずつ順番に実行。並列は探索の中の 4 プロセスだけ。`EGFG_CACHE` は外す）
- 仕様：`docs/superpowers/specs/2026-10-07-partition-speed-design.md`、計画：`docs/superpowers/plans/2026-10-07-partition-speed.md`

## 1. 何をしたか

フェーズ K の分割の探索（`optimize(..., partition="search")`）に、次の 3 つを入れた。

1. **候補の木の絞り込み**（successive halving、`partition_trees="halving"`）
   - 全ての木で合併を 2 手ずつ進め、演算回数の良い半分を残す。1 本になるまで繰り返す。
2. **候補の並列評価**（`partition_jobs`）
   - 優先順位の上位 2 × ワーカー数の候補について、まだ解いていない局所問題をプロセスのプールで同時に解く。
   - その後、候補を先頭から順に評価し、最初に減る手を採用する。
3. **手の整理**（`partition_moves`）
   - 分割の手を外した。
   - 因子の付け替えを、境目の分離集合に入っている因子だけに限った。

フェーズ K と同じ 11 問で、設定を 1 つずつ足して比べた。どの設定も交換の段階まで行い、境目の段階は行わない。

## 2. 結論の要約

全部入り（絞り込み + 並列 + 手の整理）は、フェーズ K の **0.52 倍の時間**（幾何平均、0.21〜0.94 倍）で、演算回数の悪化は **+0.13%**（最大 +0.69%）だった。

1. **H27（木の絞り込み）：一部だけ「はい」。**
   - **時間**：木が 3〜4 本で合併が長く続く問題で大きく減った。
     - 因子型 HMM：70 → 20 秒（0.29 倍）
     - 結合 HMM：57 → 28 秒（0.49 倍）
     - 格子 6×6：139 → 83 秒（0.60 倍）
   - **減らなかった問題**：格子 5×5、疎 20 変数、小さい問題。どの木も 1〜2 ラウンドで合併が止まる。止まったと分かるまでに全ての合併の候補を解く必要があるので、木を絞っても仕事が減らない。全体の幾何平均は 0.81 倍。
   - **品質**：悪化は因子型 HMM の 1 問だけで、+0.62%（5,850 → 5,886）。2 手の時点で先行していた木が、最後には負けた。目標の 0.5% 以内をわずかに超えた。格子 6×6 の良い木（−1.3%）は残った。
2. **H28（並列）：手の列は「はい」、速さは「いいえ」。**
   - 採用された手の列は、11 問すべてで並列なしと完全に一致した。
   - 速くなったのは 0.95〜2.18 倍（幾何平均 1.53 倍）。2 倍を超えたのは 3 問（鎖 64、疎 20、格子 4×4）。
   - 伸びが小さい理由は 2 つある。
     - 窓の先頭近くで手が採用されると、窓の残りの候補は先読みが無駄になる（結果は覚えておくが、後で使われないことが多い）。
     - 新しく解く局所問題が窓の中に 1〜2 個しかないことが多く、4 プロセスを使い切れない。
3. **手の整理：時間はほとんど変わらず、品質が少し落ちた。**
   - 時間は 0.53 → 0.52 倍だった。
   - 格子 4×4 で +0.69%、格子 6×6 で +0.11% 悪くなった。境目から離れた因子の付け替えが効く場合があった。
   - そこで、既定の手は、分割だけを外し、因子の付け替えはフェーズ K と同じ（スコープを含む任意のクラスタへ）にした（`EXCHANGE = ("merge", "move", "factor_any")`）。分割の手は、フェーズ K と L のどの実行でも 1 度も採用されていない。
4. **H29（予算との比較）：「いいえ」。**
   - 全部入りが固定の予算 5 通りより速かったのは 11 問中 4 問（疎 10、輪 16、結合 HMM、鎖 64）。
   - min-fill の木だけにすると 6 問で速くなった。ただし、疎 20 で +6.4% 悪化し、予算の最良（2,352）にも負けた（2,397）。
   - 演算回数は、どの設定でも予算の最良より良いか同じだった（min-fill の木だけの疎 20 を除く）。

## 4. 分かったこと

1. 速さの効き目は、絞り込み（木が多く、合併が長く続く問題）と並列（解く回数が多い問題）で、効く問題が違う。両方を入れると、時間はおよそ半分になった。
2. 残る時間の多くは、「もう減る手がない」と確かめるための最後の 1 周である。その周では、全ての候補の局所問題を解く必要がある。並列でも、この部分は窓が小さいと伸びない。
3. 次に速くするなら、候補の局所問題を本気で解く前に、安く見積もる方法が考えられる。たとえば、小さなノード上限や短い時間で解いて、減りそうな候補だけを本気で解く。最後の 1 周の大部分は「減らない」と分かればよい候補なので、効く余地が大きい。
4. 手の整理は、時間がほとんど変わらなかった。手の数を減らすより、1 回あたりの解く重さを減らすほうが効く。
