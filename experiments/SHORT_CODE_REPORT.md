# 実験レポート（フェーズ J）：出力コードを短くする

- 日付：2026-10-07
- データ：`results/short_code.csv`、ログ：`results/short_code.log`
- 再現：`uv run python experiments/short_code.py --out results/short_code.csv`（時間を測るので順番に実行。`EGFG_CACHE` は外す）
- 仕様：`docs/superpowers/specs/2026-10-07-short-code-design.md`、計画：`docs/superpowers/plans/2026-10-07-short-code.md`

## 1. 何をしたか

C のコード生成に、短いコードを出す版（compact）を足した。同じ抽出結果を、今までの版（plain）と compact の両方で書き、比べた。

- 同じ形（状態数と歩幅。変数の名前によらない）のループの入れ子を、1 つのカーネル関数にまとめる。
- 依存関係を守ったまま、同じカーネルの呼び出しが続くように並べ直す。
- 中間の配列を、大きさごとの 2 次元の配列（プール）にまとめる。
- 同じカーネルの呼び出しの連続を、ループ 1 つにする。配列の番号が一定の幅でずれるならその式で、そうでなければ番号の定数の表で回す。答えの書き出しも同じようにまとめる。
- 抽出のオプション：形の種類 × α を、貪欲な抽出のコストに足す。

問題は 24 問（arena の公開 16 問、大きめの 5 問、分割を使った鎖 64・128 変数と格子 6×6）。

## 2. 結論の要約

1. **正しさ**：全 24 問で、compact の出力は、参照（arena の問題は参照の周辺分布、他は plain）と一致した（最大誤差 8e-15）。
2. **H21（短さ）：「はい」。** 行数は plain の 0.33 倍（幾何平均）、gcc の時間は 0.40 倍。
   - 鎖 128 変数：2,673 行 → 69 行（0.03 倍）、gcc 19 秒 → 0.14 秒。
   - 木 30 変数：755 行 → 80 行（0.11 倍）。
   - 鎖と木では、長さによらずほぼ一定の行数になった。
   - 格子では効果が小さい（0.57〜0.69 倍）。ループのある構造は、計算の形の種類が多い（格子 6×6 で 97 種類）。
3. **H22（速さ）：平均では同じだが、小さい問題で遅くなる。** 実行時間は 0.96 倍（幾何平均）で、0.41〜2.52 倍に散らばった。
   - 大きい問題は速くなった：鎖 32 変数・K = 32 で 0.52 倍、格子 6×6 で 0.41 倍、鎖 64・128 変数で 0.72〜0.76 倍。
   - 数十 ns の小さい問題は遅くなった：低ランクの輪 6 変数で 2.52 倍（47 → 119 ns）、星形で 1.6 倍、木 9 変数で 1.35 倍。関数呼び出しと、番号の表を引く手間が、計算そのものに比べて大きいため。
   - そこで、arena の egfg のコンパイル（`egfg_c_program`）は、plain と compact の両方を試して速いほうを選ぶようにした。
4. **H23（抽出の α）：効果は小さい。** カーネルの種類は 1〜4 減る程度で、増える場合もあった。演算回数が増える場合もあった（輪 10 変数で 2,496 → 2,656）。抽出の段階の「形」は融合（和の連続とその下の積を 1 つのループにする処理）の前の形なので、実際のカーネルと一致しない。また、貪欲な抽出は局所解に止まる。

## 4. 分かったこと

1. egfg の DAG の段階で構造を使うと、汎用の最適化器に頼らずにコードを短くでき、gcc の時間も大きく減った。鎖と木では、長さによらない一定の大きさのコードになった。
2. 大きい問題では実行も速くなった。展開しすぎたコードより、小さなカーネルを回すほうが、命令キャッシュや gcc の最適化に有利なためと考えられる。
3. 小さい問題では、呼び出しと表引きの手間で遅くなる。問題ごとに速いほうを選べば両方の利点が得られる（arena ではそうした）。
4. ループのある構造（格子、輪）では計算の形の種類が多く、短くなりにくい。抽出で形をそろえる α は、今の「形」の定義（融合の前）と貪欲な抽出では、ほとんど効かなかった。融合の後の形で数えることが次の課題。
