# 実験レポート（フェーズ C）：観測が届いてからの計算を小さくする

- 日付：2026-10-06
- データ：`results/incremental.csv`（7 モデル × 12 設定、全 84 行）、ログ：`results/incremental.log`
- 再現：`uv run python experiments/incremental.py --out results/incremental.csv`（3 プロセス並列で約 6 分）。簡易版は `--quick`（約 4 秒）。
- 仕様：`docs/superpowers/specs/2026-10-06-incremental-cost-design.md`、計画：`docs/superpowers/plans/2026-10-06-incremental-cost.md`

## 1. 何を調べたか

オンラインのフィルタリングでは、観測と観測の間に空き時間があります。前の時刻の推定が終わってから次の観測が届くまでの間に、観測によらない計算を済ませておけます。そこで、1 ステップの計算を次の 2 つに分けました。

- 準備：そのステップの観測の因子を含まない計算。観測が届く前に済ませておける。
- 待ち時間：観測の因子を含む計算。観測が届いてからでないとできない。

e-graph の規則は項に含まれる因子の集合を変えないので、「観測を含むか」は e-class ごとに決まります。そこで抽出のとき、観測を含む e-class のコストに重みをかけて、待ち時間を重く見るようにしました。

| 目的 | 意味 |
|---|---|
| total | 合計を最小（フェーズ B と同じ） |
| latency | 待ち時間を最小にし、その中で合計を最小 |
| weighted:λ | 待ち時間を λ 倍重く見る（λ = 2、4、10） |

探索は 2 種類です。light（規則は最小限、貪欲 DAG 抽出）と default（規則はすべて、ILP 抽出）。どちらも種まきありです。比べる相手は、前向きアルゴリズム（forward）と 1 ステップのジャンクションツリー（jt）です。モデルはフェーズ B と同じ 7 つ（K = 3）で、T = 64 で値を確かめました。

## 2. 結論の要約

1. **H6：「はい」（探索が最後まで終わったモデルでは）。** 待ち時間を最小にすると、e-graph は「予測を先に済ませ、観測が届いたら更新だけする」形を見つけました。
   - 待ち時間のコストは、前向きアルゴリズムと同じか、それより小さくなりました（探索が最後まで終わったモデルで 0.89〜1.00 倍）。
   - しかも準備のコストは、HMM では前向きアルゴリズムと同じで、鎖が 2〜4 本のモデルでは 2 分の 1〜10 分の 1 でした（鎖を 1 本ずつ予測するため。フェーズ B と同じ工夫）。
   - 例外は結合 HMM の 4 本です。e-graph がノード上限に達し、light の weighted:2・weighted:4 だけ、待ち時間が前向きアルゴリズムより 3% 大きくなりました。
2. **H7：「合計最小の計算は待ち時間が大きいことがある」も「はい」。** 待ち時間を最小にしても、合計はほとんど増えませんでした。
   - 合計を最小にした計算（total）は、前向きアルゴリズムの 1.7〜3.8 倍の待ち時間を持つことがありました（fhmm3・fhmm4 の light、chmm2〜4）。観測の因子を早めに掛けて、その後の計算をすべて観測待ちにしてしまうためです。
   - latency にすると、待ち時間は total の 0.27〜0.52 倍に減りました。合計の増加は最大 2.9%（chmm3 の default）で、多くの場合は合計も同じか、むしろ減りました。
   - 合計が減ったのは、貪欲 DAG 抽出が total では局所的な最適解で止まっていたのに対し、重みを変えると別の、合計でも安い計算にたどり着いたためです。
3. **ジャンクションツリーは待ち時間が大きい。** 前向きアルゴリズムの 2.9〜10.8 倍でした。観測の因子をクリークの中で早めに掛けるためです。合計が安くても、オンラインには向きません。
4. **実時間**：`update()` の実時間は 1 ステップ 0.04〜0.5 ミリ秒でした。この規模では Python の処理の手間が大半で、コストの差は実時間にほとんど表れませんでした。
5. **正しさ**：84 行すべてで、フィルタリングの答えが参照の値と一致しました。

読み取れること：

- 待ち時間を最小にした計算は、どのモデルでも準備に「鎖を 1 本ずつ予測する」計算を使い、観測の因子は最後にまとめて掛けていました。前向きアルゴリズムと同じ「予測 → 更新」の分け方を、e-graph が自分で見つけたことになります。
- fhmm4 の default（333 対 360）と chmm3（144 対 162）では、待ち時間が前向きアルゴリズムより小さくなりました。観測が届いた後の計算（観測の因子を掛け、メッセージと周辺分布の和をとる部分）の順序を変えて安くしていると考えられますが、計算の中身はまだ詳しく確かめていません。
- 合計を最小にする場合、ILP（default）は fhmm3・fhmm4 で最初から待ち時間の小さい計算を選びました。合計の最適解と待ち時間の最適解が一致するモデルもあります。

## 4. 注意点

- **chmm4 は探索が終わっていない**：e-graph がノード上限（5 万）に達し、default は ILP が時間切れで最適解を得られませんでした（探索に 133〜157 秒）。そのため、latency より weighted:10 のほうが待ち時間が小さい、という逆転が起きています。もっと良い計算がある可能性があります。
- **貪欲 DAG 抽出の弱さ**：light の weighted:2 は、chmm3 で合計最小の計算から抜け出せませんでした。局所的な改善だけでは、計算の形を大きく変えられないためです。
- **実時間との関係**：今の規模では、評価の実時間は Python の処理の手間で決まり、コストの差は表れませんでした。コストと実時間の関係を見るには、状態数を大きくするか、コンパイルした実装が必要です。
- **割り算はコストに含めていない**：フェーズ B と同じです。

## 5. 次の課題

1. 準備に使える時間に上限がある場合（空き時間が足りないとき）の目的関数。
2. 観測が一部ずつ届く場合（観測の因子ごとに依存を分ける）。
3. 状態数を大きくして、コストの差が実時間に表れるかを確かめる。
