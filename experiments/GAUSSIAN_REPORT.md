- 再現：`uv run python experiments/gaussian.py --out results/gaussian.csv`（3 プロセス並列で約 35 分）。簡易版は `--quick`（約 13 秒）。
- 仕様：`docs/superpowers/specs/2026-10-06-gaussian-design.md`、計画：`docs/superpowers/plans/2026-10-06-gaussian.md`

## 1. 何を調べたか

連続のベクトル変数で、分布がすべて線形ガウスのモデルのフィルタリングを扱いました。積分はすべて閉じた式（行列の演算）で計算できます。

正規分布の値には表し方が 2 つあり、得意な演算が逆です。

| 表現 | 安い演算 | 高い演算 |
|---|---|---|
| モーメント形式（平均と共分散） | 積分（行と列を取り除くだけ）、予測、カルマンゲインによる更新 | 一般の積（逆行列が要る） |
| 情報形式（精度行列と情報ベクトル） | 積（足し算だけ） | 積分（シューア補行列、逆行列が要る） |

そこで、計算の形（どの順に掛けて、どの変数から積分するか）は今までどおり e-graph で探し、各中間結果をどちらの表現で持つかは、抽出のときに変換のコスト込みで選びました。比べる相手は次の 2 つです。

- KF：標準のカルマンフィルタ（状態全体を 1 本のベクトルにまとめ、モーメント形式だけで計算）
- IF：情報フィルタ（状態全体を 1 本のベクトルにまとめ、情報形式だけで計算）

### モデル

| 名前 | 中身 |
|---|---|
| vec(d, m) | d 次元の状態 1 本と、m 次元の観測 |
| blocks(k, b) | b 次元のブロック k 個。各ブロックは自分だけで動き、観測は全ブロックをまとめて 1 つ（因子型） |
| coupled(k, b) | b 次元のブロック k 個。ブロック i は自分とブロック i−1 で動き、観測はブロックごとに 1 つ（結合型） |

### 設定

- 探索：light（規則は最小限、貪欲 DAG 抽出）と default（規則はすべて、ILP 抽出、1 回の制限時間 20 秒）。どちらも種まきあり。
- 表現：both（モーメント形式と情報形式の両方）と info（情報形式だけ）。
- 目的：total（合計を最小）と latency（待ち時間を最小、フェーズ C）。
- パラメータだけで決まる計算の数え方：
  - 「毎回」（仕様どおり）：遷移や観測を情報形式にする計算を、毎ステップ数える。
  - 「1 回」（計画で追加したオプション）：遷移の情報形式や観測の HᵀR⁻¹H のように、モデルのパラメータだけで決まる部分は最初に 1 回だけ計算するとし、毎ステップは観測に依存する部分だけを数える。実際の情報フィルタはこの形で実装する。

## 2. 結論の要約

1. **H8（表現の選択）：「はい」。** 状態が 1 本のベクトルのモデルでは、e-graph はつねに KF と IF のうち安いほう以下になりました。
   - 「毎回」の数え方では、どのモデルでも KF が安く、e-graph も KF と同じ計算を選びました。
   - 「1 回」の数え方では、観測の次元 m が大きいと IF が安くなり（d=4・8 では m ≥ d、d=2 では m=4 で）、e-graph もそれに合わせました（d=8, m=16 で 1984 対 KF 8192）。
   - さらに、どちらよりも安い混合型を見つけた場合がありました。予測はモーメント形式、更新は情報形式という形で、d=2・m=4 では 44 でした（KF 128、IF 52）。
2. **H9（構造の利用）：「はい」。** 状態がブロックに分かれたモデルでは、KF よりはっきり安い計算を見つけました。
   - 因子型（blocks）：KF の 0.28〜0.57 倍。ブロックが多いほど差が大きく、4 ブロックで 0.28 倍です。
   - 結合型（coupled）：KF の 0.44〜0.68 倍。4 ブロックでは e-graph がノード上限に達しましたが、それでも 0.68 倍でした。
   - 理由は、フェーズ B の因子型 HMM と同じです。予測を「ブロックごとに、そのブロックの遷移を掛けて、前の時刻の変数を消す」形で行い、全体の大きな共分散を一度に作らないようにしていました。
3. **H10（待ち時間）：部分的に「はい」。**
   - 結合型では、待ち時間を目的にすると待ち時間がさらに下がりました（coupled(4, 2) で 1496 → 688）。KF の待ち時間（1536）の 0.45 倍です。
   - ただし合計が大きく増える場合もありました（coupled(3, 4) で合計が 1.6 倍）。
   - vec と blocks では、合計最小の計算がすでに待ち時間も最小でした。
4. **探索の時間**：light は最大 8 秒でした。default（ILP）は 20 秒の制限時間に何度も達し、結合型の 3〜4 ブロックでは探索に 48〜191 秒かかりました。しかも結果が light より悪くなることがありました（5 章）。
5. **正しさ**：464 行すべてで、各時刻の平均・共分散・対数尤度が、numpy で直接書いた参照のカルマンフィルタと一致しました（相対誤差 1e-8 以内）。

- 状態が 1 本のベクトルでは、計算の順序に選ぶ余地はありません。e-graph が選んでいるのは表現だけです。
- 「毎回」の数え方では、IF が観測を情報形式にするたびに逆行列が要り、つねに KF より高くなります。この数え方は実際の IF の実装と合っていません。
- 「1 回」の数え方にすると、m が大きいほど IF が有利になります。KF の更新が m³ に比例するのに対し、IF の更新は足し算で済むためです。
- d=2・m=4 で見つかった混合型は、次のような計算でした（演算の内訳から）。
  1. モーメント形式のまま予測（遷移を掛けて前の時刻の状態を消す）。
  2. 情報形式に変換。
  3. 観測（情報形式、パラメータの部分は計算済み）を足す。
  4. 答えを読むためにモーメント形式に戻す。

  予測は KF が、更新は IF が得意なので、その組み合わせです。2 回の変換（2×2 の逆行列）が、KF の更新（4×4 の逆行列を含む）より安いために得をしています。

## 4. 待ち時間（H10）

light・both の結果で、「準備 ＋ 待ち時間」の内訳です（「毎回」の数え方）。

| モデル | KF | e-graph（total） | e-graph（latency） |
|---|---|---|---|
| vec(4, 4) | 128 ＋ 192 | 128 ＋ 192 | 128 ＋ 192 |
| blocks(4, 2) | 1024 ＋ 168 | 160 ＋ 168 | 160 ＋ 168 |
| coupled(2, 2) | 128 ＋ 192 | 48 ＋ 136 | 72 ＋ 112 |
| coupled(3, 2) | 432 ＋ 648 | 160 ＋ 312 | 160 ＋ 312 |
| coupled(3, 4) | 3456 ＋ 5184 | 1280 ＋ 2496 | 3776 ＋ 2272 |
| coupled(4, 2) | 1024 ＋ 1536 | 240 ＋ 1496 | 1136 ＋ 688 |
| coupled(4, 4) | 8192 ＋ 12288 | 6000 ＋ 7824 | 7488 ＋ 4480 |

- 合計を最小にしただけで、e-graph の待ち時間は KF 以下になっていました（因子型では同じ、結合型では小さい）。
- 待ち時間を目的にすると、結合型では待ち時間がさらに下がりました（coupled(4, 2) で 1496 → 688）。準備（観測の前に済ませられる計算）が増える形です。
- ただし、coupled(3, 4) のように、待ち時間を 9% 下げるために合計が 1.6 倍になる場合もありました。待ち時間を最優先にする目的なので、仕様どおりの動きです。実際に使うときは、weighted:λ のように兼ね合いを調整する目的のほうが向いている場合があります。

## 5. 注意点

- **ILP（default）が貪欲 DAG 抽出（light）より悪くなる場合がある**
  - 結合型の 3〜4 ブロックでは、ILP が 20 秒の制限時間に達して最適解に届かず、light より悪い結果になりました（coupled(3, 4)、「毎回」で 7632 対 3776）。
  - 時間切れのとき、ILP は出発点（木抽出か種）の解に戻るだけで、改善した解を持っていないためです。規則がすべての設定では、e-graph が大きいことも影響しています。
  - ILP の時間切れのときに貪欲 DAG 抽出の結果も候補にする、といった改善が必要です。
- **両方の表現を使えるのに、情報形式だけより悪い場合がある**：結合型の 4 ブロック（上限で打ち切り）では、light で both（13824）が info（13472）より悪くなりました。貪欲 DAG 抽出の局所的な改善が止まったためです。理論上は both ≤ info のはずなので、探索の弱さによるものです。
- **「1 回」の数え方は計画で追加したもの**：仕様の数え方（「毎回」）では、IF が実際より高く数えられます。表には両方を載せました。
- **共分散の計算は、本来すべて前もってできる**：線形ガウスでは、共分散とカルマンゲインは観測の値によりません。今の実装は平均と共分散をひとまとまりの値として扱うので、この性質を使っていません。平均と共分散を分けて扱えば、待ち時間はさらに大きく減るはずです。
- **コストの数え方は密な行列での目安**：疎な行列の構造、数値的な安定性、実際の計算機での速さは反映していません。

## 6. 次の課題

1. 平均と共分散を別の値として扱い、観測によらない共分散の計算を準備に回す（待ち時間を大きく減らせる見込み）。
2. ILP の時間切れのときの代替を改善する（貪欲 DAG 抽出の結果も候補にする）。
3. 離散と連続が混ざるモデル（条件付き線形ガウス、D2）。
4. 抽出した計算のコード生成と、実時間での比較。
