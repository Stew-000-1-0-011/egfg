# 実験レポート（フェーズ A）：探索を軽くすると、どこまで大きな問題を解けるか

- 日付：2026-10-06
- データ：`results/scaling.csv`（全 569 回の実行）、ログ：`results/scaling.log`
- 再現：`uv run python experiments/scaling.py --out results/scaling.csv`（3 プロセス並列で約 74 分）。簡易版は `--quick`（約 20 秒）。
- 仕様：`docs/superpowers/specs/2026-10-06-search-speed-design.md`、計画：`docs/superpowers/plans/2026-10-06-search-speed.md`

## 1. 何を調べたか

フェーズ 1 では、変数が 8〜12 個程度で探索が行き詰まりました。原因は 2 つありました。e-graph が変数 1 個ごとに約 4 倍に大きくなることと、ILP 抽出が遅いことです。

そこで、探索を軽くする 4 つの「つまみ」を用意し、1 つずつ、または組み合わせて変えながら、変数の数 n を 4 から 64 まで増やしました。

| つまみ | 中身 |
|---|---|
| R（規則セット） | 書き換え規則を減らす。`no_reverse`：分配則の逆向きを除く。`minimal`：さらに結合律の片方向を除く |
| D（分割） | ジャンクションツリーのクリークを、変数がたかだか D 個の「クラスタ」にまとめ、クラスタごとに別々の小さな e-graph で探索する。クラスタ間のやりとり（メッセージ）は「入力の葉」として受け渡し、最後につなぎ合わせる |
| S（種まき） | 各クエリに、ジャンクションツリー（JT）の計算を最初から「同じもの」として登録しておく。探索が途中で打ち切られても、JT より悪い答えにはならない |
| X（抽出法） | `ilp`（最適、遅い）、`tree`（クエリごとに独立に最安、速い）、`greedy`（木抽出から始めて、共有を考えた局所改善をする） |

設定は次の 12 通りです。

| 名前 | R | D | S | X |
|---|---|---|---|---|
| base（フェーズ 1 と同じ） | full | なし | なし | ilp |
| R=no_reverse / R=minimal | 変える | なし | なし | ilp |
| D=3 / D=5 / D=8 | full | 変える | なし | ilp |
| S=on | full | なし | あり | ilp |
| X=tree / X=greedy | full | なし | なし | 変える |
| light（軽量） | minimal | 3 | あり | greedy |
| mid（中間） | no_reverse | 5 | あり | greedy |
| precise（精密） | no_reverse | 5 | あり | ilp |

問題は 7 種類です。鎖（chain）、星形（star）、ランダムな木（random_tree）、輪（cycle）、2 行の格子（grid2）、3 行の格子（grid3）、ランダムな疎グラフ（random_sparse：ランダムな木に n/4 本の辺を足したもの）。状態数は K = 3 です。ランダムな木と疎グラフは、乱数の種 0 と 1 の 2 つで試しました（表では「種 0 / 種 1」の順に並べています）。

### 壁の決め方

1 回の実行で、時間が 120 秒を超えるか、どれかの e-graph のノード数が上限（5 万）を超えたら「壁」とし、その設定・種類ではそれより大きい n を実行しませんでした。120 秒を大きく超えた実行は外から打ち切りました（表の「打切」）。

## 2. 結論の要約

1. **効いたのは分割（D）だけ。** 分割なしの設定は、どのつまみを変えても n = 8〜12 で壁に当たりました。分割を入れると壁が大きく動き、D=3 では星形以外のすべての種類で n = 48〜64 まで解けました（D=5 は 1 つの e-graph が大きいぶん ILP が遅く、種類によっては n = 16〜32 で時間の壁に当たりました）。
2. **分割しても、コストはほとんど損をしない。** 基準設定が壁に当たらずに解けた規模で比べると、D=5 のコストは基準と同じか、少し安い（ILP が時間切れで最適でなかった場合）か、最大 2.6% 高いだけでした。木（鎖・星形・ランダムな木）では完全に同じでした。大きな n でも、コストは JT の 0.55〜0.85 倍で、JT より安いままです。
3. **分割すると、次の壁は ILP の時間になる。** 分割ありで ILP を使う設定（D=3、D=5、precise）では、時間のほとんどが抽出でした。ここで貪欲 DAG 抽出に替えると（light、mid）、同じ規模が 1〜7 秒で解け、コストの損失は平均 0〜8%、最大 20% でした。
4. **種まき（S）は「壁に当たったときの保険」として効いた。** 壁に当たった実行で、基準設定は星形以外で JT の 3.8〜335 倍という非常に悪い答えを返しました。種まきありでは、同じ状況で JT の 0.56〜1.00 倍にとどまりました。ただし、種まきだけでは壁の位置は変わりません。
5. **規則セット（R）は、ほとんど効かなかった。** 除いた規則は、残りの規則の組み合わせで同じ形を作れるため、e-graph の大きさはほぼ同じでした。
6. **星形は分割でも解けなかった。** すべての設定で n = 12 で壁に当たりました（理由は 4 章）。
7. **正しさ**：打ち切られなかった 552 回すべてで、周辺分布が正しい値（n ≤ 12 は総当たり、それより大きい n はジャンクションツリー）と一致しました。不一致は 0 回、エラーも 0 回でした。

読み取れること：

- 分割なしの 6 設定（base、R、S、X）は、壁の位置がほぼ同じです。つまり「e-graph が大きくなりすぎる」という壁には、規則を減らす・種をまく・抽出を替える、のどれも効きません。

- D=3 と D=5 で初めて壁が大きく動きました。light（D=3＋貪欲）は、星形以外で 1 度も壁に当たりませんでした。

## 4. 各つまみがどの壁に効いたか

### 4.1 分割（D）：e-graph の大きさの壁に効く

分割すると、1 つの e-graph が受け持つのはクラスタの中の因子と、隣のクラスタからの入力だけになります。そのため e-graph の大きさは、問題全体ではなくクラスタの大きさで決まります。実際、成功した実行での e-graph の最大ノード数は、分割なしの base で 11 万なのに対し、D=3 では 2.8 万、D=5 では 3.5 万でした。分割なしでは n = 12 で 11 万ノードに達していたのが、D=3 では n = 64 でも、1 つのクラスタの e-graph は多くが数千ノード、最大でも 3 万ノード弱です。

一方、D=5 は D=3 より 1 つの e-graph が大きく、そのぶん ILP が遅くなりました。ランダムな木や疎グラフで、D=5 が D=3 より先に時間の壁に当たったのはこのためです。

### 4.2 抽出法（X）：分割した後の「ILP の時間」の壁に効く

分割ありで ILP を使うと、時間のほとんどが ILP に使われました（例：3 行の格子 n = 63 で D=5 は 104 秒のうち抽出がほぼすべて）。貪欲 DAG 抽出に替えた mid では、同じ問題が 3.8 秒でした。

同じ分割で ILP と貪欲を比べたコストの比（mid ÷ precise）は次のとおりです。

| 種類 | 平均 | 最大 |
|---|---|---|
| 鎖 | 1.000 | 1.000 |
| 星形 | 0.996 | 1.038 |
| ランダムな木 | 1.007 | 1.017 |
| 輪 | 1.009 | 1.036 |
| 2 行の格子 | 1.063 | 1.123 |
| 3 行の格子 | 1.083 | 1.183 |
| 疎グラフ | 1.067 | 1.133 |

木や輪ではほとんど損がなく、格子や疎グラフでは平均 6〜8%、最大 18% 高くなりました。（星形で 1 を下回るのは、ILP が時間切れで最適解を得られなかった実行があるためです。）

分割なしで抽出法だけを替えた場合（X=tree、X=greedy）は、ノード上限の壁は動きませんでした。ただし、壁に当たる直前の規模でも数秒で終わる点は、ILP（60 秒以上）と大きく違います。

### 4.3 種まき（S）：壁に当たったときの答えの悪さに効く

ノード上限で探索が打ち切られると、e-graph には「よい計算の形」がまだできていないことがあります。種まきなしの設定では、そのとき抽出される計算が非常に悪くなりました。

| 種類（壁に当たった n） | base | X=greedy | S=on |
|---|---|---|---|
| 鎖（12） | JT の 335 倍 | 335 倍 | 1.00 倍 |
| 星形（8） | 0.96 倍 | 1.22 倍 | 0.56 倍 |
| 2 行の格子（8） | 3.84 倍 | 2.75 倍 | 0.81 倍 |
| 疎グラフ（8、種 0 / 種 1） | 3.96 / 3.91 倍 | 4.05 / 3.90 倍 | 0.68 / 0.70 倍 |

種まきありでは、仕様どおり「JT 以下」が守られ、さらに JT より安い計算も見つかっています。分割ありの組み合わせ（light、mid、precise）でも種をまいているので、ノード上限に当たった実行（星形 n = 12、ランダムな木 n = 48）でもコストは JT の 0.46〜0.68 倍でした。

ただし、種まきは e-graph を小さくしないので、壁の位置自体は変わりませんでした。また、ランダムな木・輪・3 行の格子の n = 9〜12 では、種まきありでも ILP が 120 秒を超えて打ち切られました。

### 4.4 規則セット（R）：ほとんど効かなかった

壁に当たらなかった実行で e-graph のノード数を比べると、`no_reverse` は base とまったく同じ（最大でも 0.1% 差）でした。`minimal` は種類によって 0.66〜1.4 倍とばらつき、小さくなるとは限りませんでした。

理由：除いた規則は、残りの規則から作れる形しか生まないためです。たとえば `a*(b*c) → (a*b)*c` は、交換律と逆向きの結合律を組み合わせれば同じ形が作れます。分配則の逆向きも、ここで使った問題では新しい形をほとんど生みませんでした。e-graph の大きさを本当に減らすには、規則を「除く」のではなく、規則の適用の仕方（どの順序でどこまで適用するか）を変える必要があると考えられます。

なお、規則を減らしてもコストは悪化しませんでした（壁に当たらなかった規模では base と同じか安い）。

### 4.5 星形が分割でも解けなかった理由

星形では、すべてのクリークが中心の変数を含みます。分割すると、中心の変数を受け持つクラスタに、ほかのすべてのクラスタからのメッセージが集まります。n = 12 では、1 つのクラスタが 10 個前後の因子と入力の積を扱うことになり、その e-graph が分割なしの場合と同じように大きくなりました（light で 13 万ノード）。

分割の予算は「クラスタの変数の数」を制限しますが、「クラスタで掛け合わせるものの個数」は制限しません。星形のように 1 つの変数に多くの因子がつながる形では、後者を制限する工夫（積を小分けにする、など）が必要です。

## 6. 分割によるコストの損失

基準設定が壁に当たらずに解けた規模（n ≤ 8 程度）で、各設定のコストを基準と比べました（最小〜最大）。

## 7. 注意点

- **並列実行**：全体の時間を抑えるため、3 つの系列を同時に実行しました（各実行は別プロセス）。時間の測定には多少の影響があるかもしれません。
- **ILP の時間制限**：ILP 自体の時間制限は 60 秒ですが、問題の組み立てや、分割ありの場合のクラスタごとの ILP の合計で、1 回の実行が 120 秒を超えることがありました。
- **ノード上限での壁**：仕様どおり、ノード上限に達したら壁としてそれより大きい n を実行していません。種まきありの設定では、上限に達しても答えは正しく、コストも JT 以下なので、実際にはもっと大きい n まで「使える答え」が得られる可能性があります。
- **時間上限の打ち切り**：17 回の実行が打ち切られました。これらは結果がないので、コストや正しさの表には含まれていません。

## 8. 次の課題

1. **積の大きさを制限する分割**：星形のように 1 つのクラスタに多くの因子や入力が集まる場合に、積を小分けにする（クラスタの変数の数だけでなく、掛け合わせるものの個数も予算に入れる）。
2. **より速く、よりよい抽出**：分割した後の壁は ILP の時間でした。貪欲 DAG 抽出の損失（格子で最大 18%）を減らす改善（たとえば、局所的に ILP を使う）。
3. **規則の適用の仕方**：規則を除いても e-graph は小さくならなかったので、適用の順序や回数を制御する方法を試す。
4. **時刻の添字を持つテンプレート（B）**：入力の葉はすでに用意したので、前の時刻の状態を入力の葉として扱う。
