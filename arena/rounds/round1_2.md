# ラウンド 1・2 の記録（二者の対戦の試行）

## ラウンド 1（Python の約束）

- 書く側（LLM）：16 問すべて正しい。egfg：16 問すべて正しい。
- 速さ：書く側が 16 問すべてで勝ち。egfg ÷ 書く側の時間の幾何平均は 3.6 倍（2 回の採点で同じ）。
- 原因：表が小さいので、numpy の呼び出し回数で時間が決まっていた（einsum 1 回 1.6〜2.9 µs、.dot 0.7 µs）。egfg は演算回数を最小にしていたが、呼び出しの回数は多かった。低ランクの問題では、実行時の特異値分解（15〜22 µs）で大きく遅れた。
- 書く側の工夫：呼び出し回数を数える、まとめて計算する（行列の積をまとめる）、正規化の定数を共通にする、低ランクは得をするときだけ使う（ランク 1 は閉じた式）。
- 判断：呼び出しの手間に左右されないよう、対戦を C に切り替えた。

## ラウンド 2（C の約束）

### 採点の修正

- 書く側の報告で、ctypes の呼び出しの手間（0.33〜0.45 µs）が、計算そのもの（30〜300 ns）より大きいと分かった。C の中のループで多数回呼ぶ形にして、計算の時間を測れるようにした。
- 積和の融合（FMA）は `-std=c11` で無効になるので、両側とも `-ffp-contract=fast` でコンパイルするようにした（書く側は pragma で有効にしていた）。

### egfg 側の改善（改善する側）

1. C のコード生成（入れ子のループ、表は並べ替えずに添字で読む、和と積の融合、共通の正規化）。
2. 低ランク分解の C 版：特異値分解の代わりに、選んだ行と列から作る分解（T = C·W⁻¹·R、小さな連立方程式を実行時に解く）。書く側の方法を参考にした。
3. 自動調整：コストの固定費（0、64、512）と、低ランク分解の有無を変えた版を作り、見本の表で実際に測って一番速いものを選ぶ。
4. バグの修正：和の連続を 1 つのループにまとめる処理で、連続の下が葉や共有された値のときに誤った（取り置きの問題で見つかった）。

### 結果（公開の 16 問、2 回の採点）

| 段階 | egfg ÷ 書く側（幾何平均） | egfg の勝ち |
|---|---|---|
| 改善前（C、計時の修正後） | 2.2 | 3 / 16 |
| 改善後 | 1.65〜1.8 | 1〜2 / 16 |

- 低ランク：ランク 1 は 64 倍 → 1.8 倍、ランク 3 は 15 倍 → 2.9 倍に縮まった。
- 残る差：鎖・閉路・格子で 2〜3.4 倍。演算回数はほぼ同じなので、生成した C の質（ベクトル化、一時配列、依存の鎖の長さ）の差。
- 取り置きの判定（A/B、seed 7）：新しい版は前の版の 0.81 倍の時間、全問正しい → 採用。

### 書く側の主な工夫（C）

- GCC のベクトル拡張（4・8 要素のベクトル）で 3 倍程度速くなった。
- シャッフルを避ける配置（表の値をそのまま読み込んで、ベクトルはレジスタに置く）。
- 依存の鎖を短くする（木の根を中央に置き、両側を並行に計算する）。
- 構造を厳密に使う（ランク 1 は閉じた式、梯子は列を 1 つの変数にまとめる、次数 2 の経路は行列の積）。

### 採点の抜け穴の確認

- 答えの埋め込み：表の値は採点のたびに新しい種から作るので、できない。
- 範囲外への逃げ：この段階では敵役がいないので、未確認。
- 過剰な合わせ込み：取り置きの問題（構造が公開の問題と重ならない）でも改善が確認できた。
- 注意：pragma やベクトル拡張は許している（両側とも使える）。計時は ±30% 程度ぶれる。
