# 線形ガウスのフィルタ：egfg の C、カルマンフィルタ・情報フィルタの C、GTSAM（C++）、dynamax（JAX）

- 日付：2026-10-06
- 結果：`arena/results/gaussian_c.json`
- 再現：`uv run --group libs python arena/gaussian_bench/run.py --gtsam <GTSAM のインストール先> --out arena/results/gaussian_c.json`
- 新しく作ったもの：線形ガウスのフィルタのプログラムを C に書き出すコード生成（`src/egfg/gccodegen.py`）

## 比べたもの

| 名前 | 中身 |
|---|---|
| egfg_c | egfg が選んだ計算（フェーズ D の light 設定：規則は最小限、貪欲抽出、表現は両方、パラメータだけの部分は最初に 1 回）を C に書き出したもの |
| kf_c | カルマンフィルタ（状態全体を 1 本のベクトルにまとめ、モーメント形式だけ）。同じコード生成で C にしたもの |
| if_c | 情報フィルタ（状態全体を 1 本、情報形式だけ）。同じコード生成で C にしたもの |
| gtsam_kf | GTSAM の `KalmanFilter`（`predictQ`、`updateQ`）。状態全体を 1 本のベクトルにまとめたもの |
| dynamax | dynamax（JAX）の `lgssm_filter`。状態全体を 1 本にまとめ、全ステップを `lax.scan` で 1 回の jit 済みの呼び出しにしたもの。対数尤度も計算する（ほかの方式は計算しない） |
| gtsam_fg | GTSAM の因子グラフ。ブロックと時刻ごとに 1 つの変数を作り、各ステップで遷移と観測の因子を足し、前の時刻の変数を消去する（`eliminatePartialSequential`）。各ブロックの平均と共分散はベイズ木から読む |

- どれも、各ステップで全ブロックの平均と共分散を出す。対数尤度は出さない（コード生成でも省いた）。
- GTSAM の雑音の共分散は、最初に 1 回だけ白色化した。毎ステップ白色化するのは、観測の右辺だけ。
- コンパイル：`-O3 -march=native -ffp-contract=fast`（C と C++ で同じ）。
- 時間は、200 ステップの実行の 1 ステップあたりの平均を 7 回とった中央値。
- 正しさ：最初の 5 ステップの平均と共分散が、numpy の参照のカルマンフィルタと一致すること（相対誤差 1e-8 以内）。全 9 モデル × 6 方式で一致した（C と C++ は最大 1e-14 程度、dynamax は最大 8e-10）。

## 分かったこと

1. **同じコード生成どうしの比較（方法の差）では、構造のあるモデルで egfg が速い。**
   - 結合型（coupled）：KF と IF の速いほうの 0.25〜0.34 倍。
   - 因子型（blocks）：KF の 0.44〜0.93 倍。ブロックが多いほど差が大きい。
   - これはフェーズ D の演算回数の比（0.28〜0.68）とおおむね合う。ブロックごとに予測し、全体の大きな共分散を作らないことが、実時間でも効いている。
2. **状態が 1 本のベクトル（vec）では、演算回数の予想が実時間と合わない。**
   - egfg は KF と IF の速いほうの 1.15〜1.40 倍だった。
   - vec(2, 4) では混合型（演算回数 44、IF は 52）を、vec(4, 4) と vec(8, 16) では IF と同じ演算回数の計算を選んだが、どれも速いほうに負けた。
   - 原因は、コストモデルが逆行列（コレスキー分解）の定数倍や、メモリの読み書きを数えていないこと。差が小さい場面では、選択が逆になる。コストの係数を実測で合わせる必要がある（以前の論点 3）。
3. **GTSAM と dynamax との差の大部分は実装の差。**
   - GTSAM は、ステップごとに因子とグラフを作り（メモリの確保）、汎用の消去を行う。小さなモデルでは、この一定の手間（約 9µs）が支配的。
   - dynamax も小さなモデルでは 1 ステップ 3〜11µs かかる（XLA の小さな演算の一定の手間）。
   - モデルが大きくなると差は縮む。dynamax は blocks(8, 4)（状態 32 次元）で egfg より速かった（16µs 対 20µs）。状態全体の密な KF でも、最適化された行列演算（XLA）が、構造を使った素朴なループに勝つ。
   - gtsam_fg（ブロックごとの変数）は、ブロックの構造を使えるはずだが、ブロックのあるモデル（blocks、coupled）では gtsam_kf より遅かった。前の時刻の変数を消すと、今の時刻のブロックがすべてつながる（密な情報行列になる）ので、構造の利点が消え、因子グラフの手間だけが残る。
   - 方法の差として言えるのは、上の 1.（同じコード生成での 0.25〜0.93 倍）まで。大きなモデルで既存のライブラリに勝ち続けるには、生成するコードの質（行列の積のブロック化、ベクトル化）を上げる必要がある。
4. **探索の時間。** ブロックが 6〜8 個になると 32〜39 秒かかった。構造が固定なら一度だけで済むが、規模の壁は残っている。

## 注意

- egfg の C は、egfg の計算の選び方を、素朴なループでそのまま書いたもの。行列の積の最適化（ブロック化、ベクトル化）はしていない。大きなモデルでは、生成するコードの質を上げる余地がある。
- 観測は乱数（モデルとは無関係）で、フィルタの数値の正しさだけを確かめている。
