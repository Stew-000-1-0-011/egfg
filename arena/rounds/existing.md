# 同じ問題での既存手法との比較（離散、全変数の周辺分布）

- 日付：2026-10-06
- 結果：`arena/results/existing_seed401.json`（表の種 401）
- 再現：`uv run --group libs python arena/compare_existing.py --seed 401 --out arena/results/existing_seed401.json`
- 問題：公開の 16 問と、大きめの 5 問（`egfg.arena.larger_problems`：鎖 32 変数 K=32、輪 16 変数 K=16、木 30 変数 K=8、格子 4×4 K=3、低ランクの輪 12 変数 K=32）
- 正しさ：全 21 問、全方式で参照と一致（誤差 1e-6 以下）

## 何を比べたか

### 1. 計算の計画（同じコストモデル、同じ C のコード生成）

計算の計画（どの順に掛けて、どの変数から和をとるか）だけを変え、それ以外はそろえた。

| 名前 | 計画の作り方 |
|---|---|
| egfg | egfg の既定（seeds+staged、貪欲抽出、低ランク分解なし） |
| best_jt+ | 複数の消去順序のジャンクションツリーの最良（部分積の共有あり） |
| opt_einsum_dp | opt_einsum の動的計画法（`optimize="dp"`、演算回数の最小化）。周辺分布ごとに 1 つの縮約の順序 |
| cotengra | cotengra のハイパー最適化（`minimize="flops"`、32 回、kahypar あり）。周辺分布ごとに 1 つの縮約の順序 |
| egfg_tuned | arena の egfg（コストの設定を 3 通り試して実時間で選ぶ。低ランクの表では分解も使う） |

- opt_einsum と cotengra の縮約の順序は、egfg の項（Mul と Sum）に直した。等しい部分項は共有する（opt_einsum の `shared_intermediates` と同じ考え方）。
- そのあと、egfg のコストモデル（演算回数）と C のコード生成を通した。したがって、差は計画の差だけ。
- 既存のツールは周辺分布を 1 つずつ計画する。全変数の周辺分布をまとめて計画する仕組みはない（共通部分は、同じ項になったときだけ共有される）。

### 2. Python からの使い方（各ツールの実行時間）

| 名前 | 中身 |
|---|---|
| egfg_numpy | egfg が生成した numpy のプログラム |
| opt_einsum | 周辺分布ごとに事前に作った縮約の式（`contract_expression`、dp）を、`shared_intermediates` の中で呼ぶ |
| funsor | Funsor（numpy 版）。`sum_product` を遅延評価で組み立て、`apply_optimizer` で縮約する（内部で opt_einsum）。`memoize` で周辺分布の間の共通部分を共有する |

- Funsor をそのまま（即時評価で）使うと、全変数の同時分布の表を作ってしまい、メモリが足りなくなった（鎖 15 変数で 4^15 要素）。遅延評価と最適化が正しい使い方。

## 結果

### 計画（演算回数と、C での実時間）

比は「相手 ÷ egfg」の幾何平均。1 より大きいと egfg が勝ち。

| 問題の種類（問題数） | best_jt+ | opt_einsum_dp | cotengra | egfg_tuned |
|---|---|---|---|---|
| 演算回数：木・鎖・星（8） | 1.49 | 1.04 | 1.12 | 1.00 |
| 演算回数：ループあり（10） | 1.12 | 1.63 | 1.85 | 1.00 |
| 演算回数：低ランク（3） | 1.11 | 2.14 | 2.40 | 0.03 |
| 演算回数：全体（21） | 1.25 | 1.43 | 1.59 | 0.60 |
| 実時間：木・鎖・星（8） | 1.67 | **0.84** | 1.00 | 0.92 |
| 実時間：ループあり（10） | 1.26 | 1.46 | 1.73 | 1.05 |
| 実時間：低ランク（3） | 1.17 | 1.53 | 1.53 | 0.04 |
| 実時間：全体（21） | 1.39 | 1.19 | 1.38 | 0.63 |

- 演算回数では、egfg（分解なし）が全 21 問で、best_jt+・opt_einsum・cotengra のどれ以下でもあった。
- 実時間で一番速かった計画の数：opt_einsum_dp 10 問、egfg 9 問、best_jt+ 1 問、cotengra 1 問（egfg_tuned を除く）。
- 計画にかかった時間：opt_einsum の dp は小さな問題では 0.01 秒以下だが、木 30 変数で 77 秒、格子 4×4 で 174 秒かかった。egfg は 0.1〜20 秒、cotengra は 0.1〜32 秒。

### Python からの実行時間

- opt_einsum：egfg の numpy のプログラムの 1.7〜36 倍（幾何平均 12 倍）。
- Funsor：85〜2300 倍（幾何平均 600 倍）。

これは計画の差ではなく、呼び出しの手間の差。egfg のプログラムは計画が決まった直線的なコードで、opt_einsum と Funsor は呼び出しのたびにキャッシュの確認や式の組み立てをする。

## 分かったこと

1. **計画の質（演算回数）では、egfg は既存の縮約順序のツールに勝つ。差はループのある問題で大きい。**
   - 木・鎖・星では、周辺分布ごとの縮約の順序に共通部分の共有を加えるだけで、egfg とほぼ同じになった（opt_einsum で 1.04 倍）。木では、どの方法も前向き・後ろ向きのメッセージ（BP）と同じ計算に行き着く。
   - 輪・格子・疎なグラフでは、opt_einsum と cotengra は 1.6〜1.9 倍の演算をした。周辺分布ごとに別の順序を選ぶので、途中結果がそろわず、共有できない。全変数の周辺分布をまとめて計画することが効いている。
   - best_jt+ は、ループありでは egfg に近い（1.12 倍）が、木では弱い（1.49 倍）。
   - 低ランクの表では、分解を使える egfg_tuned だけが大きく安い（0.03 倍）。既存のツールには、表の値の構造を使う仕組みがない。
2. **ただし実時間では、木・鎖・星で opt_einsum の計画の方が速かった（0.84 倍）。**
   - 演算回数はほぼ同じなのに、鎖 32 変数では egfg の 2 倍近く速かった（23µs 対 45µs）。
   - 原因は未調査。計画の形（どの中間結果を作るか、その変数の並び）によって、生成した C のループの順序やメモリの読み方が変わり、演算回数に表れない差が出ていると推測している。コストモデルに、メモリの読み方を入れる必要がある（線形ガウスでの結果と同じ課題）。
3. **計画の時間。** opt_einsum の dp は大きな問題で急に遅くなる（数分）。egfg の探索は数秒〜20 秒で、問題の大きさに対して比較的安定していた。
4. **Python から使うライブラリとしての速さは、比較にならないほど違う。** ただし、これは「計画をコンパイルして直線的なコードにする」ことの効果で、e-graph の効果ではない。

## まとめ

- egfg の強み（既存のツールにないもの）：全変数の周辺分布をまとめて計画すること（ループのある問題で 1.6〜1.9 倍少ない演算）と、表の値の構造（低ランク）を使うこと。
- egfg の弱み：演算回数が同じときの実時間（木・鎖で負ける）。コストモデルとコード生成の改善が必要。
