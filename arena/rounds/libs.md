# 既存のライブラリとの比較（離散、全変数の周辺分布）

- 日付：2026-10-06
- 表の種：401（`arena/results/round2b_c_seed401.json` と同じ表）
- 結果：`arena/results/libs_seed401.json`（Python から呼んだ GTSAM と pyAgrum）、`arena/results/gtsam_cpp_seed401.json`（C++ の GTSAM）
- 比べたもの：
  - GTSAM 4.3.0（`DiscreteFactorGraph`、`DiscreteMarginals`）。Python の wheel と、ソースからのビルド（Release、`-march=native`）。
  - pyAgrum 3.2.0（`MarkovRandomField`、`ShaferShenoyMRFInference`）。Python から。
  - egfg の C、LLM の C（arena の採点と同じ時間の測り方）。

## 測り方

- グラフは一度だけ作る。測るのは推論だけ。
- GTSAM（C++）では、次の 3 つを測った。
  - 全変数の周辺分布：`DiscreteMarginals` を作り、各変数の `marginalProbabilities` を求める。
  - 消去だけ：`eliminateMultifrontal`。消去の順序（COLAMD）の計算を含む。
  - 順序を先に計算した消去：順序の計算を除く。egfg は計算の段取りをコンパイル時に決めるので、それに条件を寄せたもの。
- pyAgrum では、毎回新しい推論エンジンを作る。`makeInference` は結果をキャッシュするため。
- 時間は、多数回の呼び出しの平均を 7 組とった中央値。

## 結果

公開の 16 問と大きめの 5 問（`big_*`）の全問で、両ライブラリとも参照と一致した（誤差は 1e-6 以下）。

時間の比は、GTSAM（C++）÷ egfg の C の幾何平均。

| 対象 | 全変数の周辺分布 | 消去だけ | 順序を先に計算した消去 |
|---|---|---|---|
| 公開の 16 問 | 約 7300 倍 | 約 2200 倍 | 約 2200 倍 |
| 大きめの 5 問 | 約 7700 倍 | 約 2200 倍 | 約 1900 倍 |

大きめの問題の例（µs）：

| 問題 | GTSAM：全周辺分布 | GTSAM：消去だけ | egfg の C |
|---|---|---|---|
| 鎖 32 変数、K = 32 | 24000 | 8900 | 40 |
| 輪 16 変数、K = 16 | 92000 | 23000 | 35 |
| 格子 4×4、K = 3 | 9600 | 2200 | 0.74 |
| 輪 12 変数、K = 32、ランク 2 | 540000 | 134000 | 1.6 |

- 公開の問題では、GTSAM（C++）が 150〜20000µs、pyAgrum（Python から）が 290〜850µs。egfg の C は 0.02〜0.8µs、LLM の C は 0.02〜0.33µs。
- Python から呼んだ GTSAM の値は、C++ とほぼ同じだった。差はバインディングの手間ではない（1 回の呼び出しは約 0.1µs）。
- 時間は実行ごとに 2 倍程度ばらつく。ただし桁は変わらない。

## 解釈

- GTSAM の離散推論が遅いのは、ほぼ実装のため。
  - 表を決定木（代数的決定図）で持ち、積や和のたびに木を作り直す。値がばらばらの密な表では、要素 1 つあたりの手間が大きい。
  - 全変数の周辺分布を一度に求める仕組みがない。変数ごとにベイズ木から周辺を計算するので、消去だけの約 3 倍かかる。
  - 消去の順序を先に決めても、ほとんど変わらない。遅さの原因は順序ではなく、データ構造。
- 低ランクの表では差がさらに開く（数万〜数十万倍）。GTSAM は表の構造（ランク）を使わず、輪では状態数の 3 乗の表を作る。egfg は分解を使う。ここだけは計算の段取り（アルゴリズム）の差。
- pyAgrum も、推論のたびにジャンクションツリーと汎用のテンソル演算を使う。小さな問題では一定の手間（数百 µs）が支配的。

## 結論

- 既存のライブラリと比べること自体はできる。正しさも一致した。
- ただし、密な離散の問題で GTSAM や pyAgrum に勝っても、「egfg の方法が優れている」という主張にはならない。差の大部分は、汎用の実行時エンジンと、構造を固定して生成した C との差。
- 離散の強い比較の相手は、今までどおり LLM の C と、同じ C 生成を使ったジャンクションツリー（best-JT+）。アルゴリズムの差を示すのは、低ランクのように表の構造を使う場面。
- GTSAM の本領は線形ガウスと非線形最小二乗。意味のある比較は、フェーズ D の線形ガウスのフィルタと GTSAM（`GaussianFactorGraph`、`KalmanFilter`）を C++ で比べること。それには egfg の線形ガウスの計算を C に書き出す必要がある（未実装）。
